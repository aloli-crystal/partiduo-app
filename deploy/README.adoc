= Déploiement et exploitation du parc Partiduo
:toc: left
:toc-title: Table des matières
:icons: font

Partiduo sert *une instance par dossier* : une application, une base
PostgreSQL, une URL `<dossier>.<domaine>` (ADR-001 D2). Les serveurs sont sous
*FreeBSD* et Partiduo y est installé *par paquet*, depuis le dépôt
`pkg.aloli.net` (overlay de ports `aloli/aloli-ports`, construit par
poudriere ; distribution `aloli-crystal/partiduo-dist`). Ce répertoire outille
la création d'une instance et l'exploitation du parc, sur le modèle de
`prod-quimeo/capistrano-quimeo` (N plateformes, un vhost par plateforme,
`init` / `backup` / `drop`).

== Paquets

[cols="1,1,2",options="header"]
|===
|Paquet |Source |Installé dans

|`partiduo-app`
|branche `production` de `partiduo-dist`
|`/usr/local/lib/partiduo/`, script `rc.d` `partiduo`

|`partiduo-app-devel`
|branche `development`
|les mêmes emplacements
|===

Une seule version par serveur : les deux paquets s'installent aux mêmes
emplacements et s'excluent (`CONFLICTS_INSTALL`). La version de
développement va sur le serveur de test, la version stable sur les serveurs
de production ; la *version* d'une instance (`app` ou `devel`) n'est que le
paquet attendu sur son serveur. Chaque paquet contient le serveur, la ligne
de commande Marten (`partiduo-manage`, aussi
`/usr/local/bin/partiduo-manage`), le
convertisseur PDF de MODELES, les gabarits, traductions et fichiers statiques
(rangés à côté des programmes), `partiduo-provision` et ses gabarits. Le
compte système `partiduo` est créé à l'installation.

[cols="1,3",options="header"]
|===
|Fichier |Rôle

|`../bin/partiduo-provision`
|Crée une instance : base, migrations, société et jeu de données initial,
fichiers de service. N'installe rien sur le système.

|`templates/instance.env.tmpl`
|Environnement de l'instance : base, modules, domaine, clé secrète, port,
pièces jointes. Lu par `/bin/sh` (script `rc.d`, tâches cron).

|`templates/nginx-acme.conf.tmpl`
|Vhost d'amorçage : ne sert que les défis ACME (HTTP-01), le temps d'obtenir
le certificat de l'instance.

|`templates/nginx-vhost.conf.tmpl`
|Vhost nginx : défis ACME et redirection HTTPS, certificat Let's Encrypt
*propre à l'instance*, mandataire vers le port local de l'instance.

|`templates/partiduo-instance.cron.tmpl`
|Tâches quotidiennes de l'instance (fin de mois de la Facturation), pour
`cron(8)`.

|`bin/partiduo-fleet`
|Exploitation du parc : provisionnement, état, sauvegardes, retrait.

|`fleet.conf.example`, `inventory.example`
|Configuration du parc et inventaire des instances (à copier en `fleet.conf`
et `inventory`, ignorés par git).
|===

== Créer une instance : `partiduo-provision`

Sur un serveur, en tant que `partiduo` : le script du paquet de la version
voulue (`partiduo-fleet provision` le fait à distance).

[source,sh]
----
/usr/local/lib/partiduo/bin/partiduo-provision --name "Exemple SARL" --regime fr \
  --siren 732829320 --modules accounting,invoicing --with skel \
  --admin-email admin@exemple.fr exemple-sarl
----

Étapes (ADR-001 D2 § Provisionnement) :

. `createdb --owner=<rôle> --encoding=UTF8 partiduo_<dossier>` (`--owner`,
  `--database`, `--skip-createdb` ; `--files-only` saute les étapes 1 à 3
  pour une base déjà remplie, restauration dans une instance neuve,
  D-AFN-009) ;
. `migrate` sur cette base, avec `PARTIDUO_MODULES` = modules + extensions ;
. commande Marten `provision` : société (`Settings`, ligne unique) puis jeu de
  données initial des pièces actives, selon le régime (`--regime fr|be`), par
  `Partiduo::Api::Core.provision` — une seule transaction ; avec
  `--admin-email`, le lien d'invitation de l'administrateur est affiché, à lui
  transmettre (D-J1-001) ;
. génération, dans `--output-dir` (défaut `./tmp/instances/<dossier>/`), de
  `<dossier>.env` (mode 600, clé secrète aléatoire), `<dossier>.acme.nginx.conf`,
  `<dossier>.nginx.conf`, `partiduo-<dossier>.cron` et `INSTALL.txt`, les
  commandes d'installation (script `sh`, `set -eu`) — *non exécutées*.

`--version app|devel` (défaut `app`) nomme le paquet qui sert l'instance
(`partiduo-app` ou `partiduo-app-devel`) ; les chemins, le script `rc.d` et
la ligne de commande sont les mêmes pour les deux.
`INSTALL.txt` vérifie d'abord que `acme.sh` est installé selon les conventions
du port (`/usr/local/sbin/acme.sh`, utilisateur `acme`, règle
`/usr/local/etc/sudoers.d/acme`) et que `nginx.conf` inclut `partiduo/*.conf`, puis
installe l'environnement (`/usr/local/etc/partiduo/<dossier>.env`,
root:partiduo, 640), crée `/var/db/partiduo/<dossier>/media`, ajoute l'instance
au script `rc.d` du paquet (`sysrc partiduo_instances+=" <dossier>"`,
`sysrc partiduo_enable=YES`, `service partiduo start <dossier>`), installe la
tâche cron (`/usr/local/etc/cron.d/partiduo-<dossier>`, à une minute tirée du
port), puis le certificat.

=== Certificat TLS : un par instance

ADR-001 D2 retient un certificat Let's Encrypt *par instance* (pas de
certificat générique). Il est obtenu par `acme.sh`, comme sur tout le parc
beryl (pas de Python sur les serveurs, D-PKG-007), avec les conventions du
port FreeBSD `security/acme.sh` que suit la recette beryl `acme` : acme.sh
tourne sous l'utilisateur `acme` (`su -m acme -c …`), *jamais en root* ; home
`/var/db/acme/.acme.sh` ; clé ECDSA (`ec-256`) ; certificat laissé dans le
`CERT_HOME` `/var/db/acme/certs`, soit
`/var/db/acme/certs/<dossier>.<domaine>_ecc/fullchain.cer` et
`<dossier>.<domaine>.key`, sans copie ailleurs. `INSTALL.txt` :

. donne le webroot (`--acme-webroot`, défaut `/usr/local/www/letsencrypt`) à
  `acme:acme`, qui y écrit les défis ;
. installe le vhost d'amorçage (`/usr/local/etc/nginx/partiduo/<dossier>.conf`,
  HTTP seul, défis ACME sur le webroot) et recharge nginx — nginx refuse un
  vhost HTTPS dont le certificat n'existe pas encore ;
. avec `--acme-email`, enregistre le compte ACME
  (`acme.sh --register-account -m <adresse>`) ;
. `acme.sh --issue --server letsencrypt -d <dossier>.<domaine> -w <webroot>
  --home /var/db/acme/.acme.sh --cert-home /var/db/acme/certs --keylength
  ec-256` : code 0, certificat émis ; code 2, certificat encore valide, rien à
  faire ; tout autre code arrête l'installation (journal
  `/var/log/acme.sh.log`) ;
. `acme.sh --install-cert -d <dossier>.<domaine> --ecc --home … --cert-home …
  --reloadcmd '/usr/local/bin/sudo /usr/sbin/service nginx reload'` : aucune
  copie, acme.sh enregistre seulement la commande de rechargement (chemins
  absolus : le cron n'a qu'un `PATH` réduit ; sudo limité à cette commande par
  la recette `acme`) ;
. installe le vhost définitif, qui lit le certificat dans `CERT_HOME`, et
  recharge nginx.

Le renouvellement est celui du cron d'acme.sh posé par la recette beryl
`acme` (`/usr/local/etc/cron.d/acme`, ligne `acme.sh-cron.d` du port :
utilisateur `acme`, `lockf`, `acme.sh --cron --home /var/db/acme/.acme.sh`,
chaque nuit), par le même webroot, que le vhost définitif continue de servir ;
acme.sh rejoue alors le `reloadcmd` enregistré à l'installation.
`--acme-email` (ou ``, lettres, chiffres et `._%+-`
seulement : l'adresse passe dans la commande confiée à `su`) désigne le compte
ACME — celui qui portera la demande de relèvement de quota (ADR-001 D2) ; sans
adresse, acme.sh enregistre un compte sans courriel.

*Quota* : 50 nouveaux certificats par semaine pour `partiduo.app`, tous
comptes confondus. `acme.sh --issue` ne réémet pas un certificat valide
(code 2) quand on rejoue `INSTALL.txt` ; `--acme-staging` utilise l'autorité
de test (`--server letsencrypt_test`), hors quota, pour les essais.
`partiduo-fleet retire` arrête le renouvellement du certificat de l'instance
retirée (`acme.sh --remove`, sous l'utilisateur `acme`) et supprime
`/var/db/acme/certs/<dossier>.<domaine>_ecc/`.

`--dry-run` affiche les étapes sans rien exécuter. La ligne de commande Marten
utilisée est `--manage`, sinon `$PARTIDUO_MANAGE`, sinon celle du paquet
(`/usr/local/bin/partiduo-manage`), sinon
`bin/partiduo-manage` à côté du script, sinon `crystal run manage.cr --`
(développement). C'est la ligne de commande de la distribution (interface +
cœur + extensions) : elle connaît les migrations *et* les extensions.

Le port HTTP local est le premier libre à partir de 8101 parmi les instances
déjà générées dans le répertoire de sortie et celles du serveur (`--port`
pour le fixer).

=== Développement

Base locale (préfixe `partiduo_`) et fichiers générés dans `./tmp/instances/` :

[source,sh]
----
bin/partiduo-provision --name "Démo" --regime be demo
# puis, dans partiduo-ui-bulma :
DATABASE_URL='postgres:///partiduo_demo?host=/tmp' crystal run src/server.cr
# http://demo.partiduo.localhost:8000/
----

== Exploiter le parc : `partiduo-fleet`

Par défaut, *chaque commande affiche son plan* (commandes locales, et
distantes préfixées du serveur) sans rien exécuter ; `--execute` exécute.

[source,sh]
----
cp deploy/fleet.conf.example deploy/fleet.conf       # domaine, chemins, comptes
cp deploy/inventory.example deploy/inventory         # « <dossier> <serveur> [app|devel] »

deploy/bin/partiduo-fleet provision deploy@srv1 exemple-sarl --name="Exemple SARL" --regime=fr
deploy/bin/partiduo-fleet provision deploy@test recette --version devel --name=Recette --regime=fr
deploy/bin/partiduo-fleet status
----

Les nouvelles versions arrivent par le dépôt `pkg.aloli.net` et c'est beryl
qui met les paquets à jour : plus de construction, d'envoi ni de montée de
version par `partiduo-fleet` (`build`, `upload`, `upgrade`, `rollback`,
`cleanup` n'existent plus).

=== Arborescence sur un serveur

[source]
----
/usr/local/lib/partiduo/                 # paquet partiduo-app ou partiduo-app-devel
├── bin/partiduo-server, partiduo-manage, partiduo-modeles-pdf, partiduo-provision
├── deploy/templates/                    # gabarits de partiduo-provision
└── share/partiduo/{artifacts,assets}/   # gabarits HTML, traductions, fichiers statiques
/usr/local/etc/rc.d/partiduo             # rc.d du paquet (partiduo_instances)
/usr/local/etc/partiduo/<dossier>.env    # root:partiduo, 640
/usr/local/etc/cron.d/partiduo-<dossier> # tâches quotidiennes
/usr/local/etc/nginx/partiduo/<dossier>.conf
/var/db/partiduo/<dossier>/media/        # pièces jointes
/var/log/partiduo/<dossier>.log          # journal du serveur (daemon -o)
/var/backups/partiduo/<dossier>/<nom>.dump      # pg_dump -Fc
/var/backups/partiduo/<dossier>/<nom>.media.tar.gz  # pièces jointes
----

=== Sauvegardes

`backup` (et la sauvegarde préalable de `upgrade` et `retire`) écrit, sous un
même nom dans `$BACKUP_DIR/<dossier>/` : `<nom>.dump` (`pg_dump -Fc`),
`<nom>.plan.json` et `<nom>.files` (réponse et liste de
`partiduo-manage instance backup-plan`, link:../doc/api/instance-cli.adoc[]),
`<nom>.media.tar.gz` (les pièces jointes listées). La liste vient de
l'instance, relevée avant et après `pg_dump` (union, D-AFN-012) : seules les
pièces enregistrées *et encore présentes* sont archivées (`bsdtar` n'a pas
l'option `--ignore-failed-read` de GNU tar), les fichiers manquants sont
signalés dans `plan.json`. `restore <dossier> <nom>.dump` remet la base puis
les pièces jointes de `<nom>.media.tar.gz` sous `$PARTIDUO_MEDIA_ROOT`.

Les sauvegardes régulières relèveront d'une infrastructure dédiée, à venir ;
celles-ci servent aux opérations de parc.

=== La mise à jour est une opération de parc

ADR-001 : « passer 300 dossiers en version N+1 suppose un outillage de
déploiement et une stratégie de migration progressive ». La stratégie retenue :

* *un seul binaire par version* (ADR-003 D1) : les extensions sont compilées
  dedans, activées par instance (`PARTIDUO_MODULES`, puis écran
  d'administration) ;
* *beryl met les paquets à jour* (`pkg upgrade`), serveur par serveur, sur
  tout le parc (instances et administration) ; le paquet est partagé par
  toutes les instances d'un serveur ;
* *le script `rc.d` migre chaque instance à son démarrage*
  (`partiduo-manage migrate` avant le serveur) : après `pkg upgrade`,
  `service partiduo restart` suffit ; une instance dont la migration échoue
  ne démarre pas, et son journal (`/var/log/partiduo/<dossier>.log`) dit
  pourquoi ;
* une instance de recette sert à éprouver la branche `development` : elle est
  servie par `partiduo-app-devel`, sur le serveur de test, qui n'a que ce
  paquet (une seule version par serveur).

=== Prérequis d'un serveur

* FreeBSD 15, dépôt `pkg.aloli.net` activé (beryl, recette `pkg-repo-aloli`) ;
  paquet `partiduo-app` (`partiduo-app-devel` sur le serveur de test : l'un
  ou l'autre, jamais les deux) ;
* PostgreSQL 18, joint *par socket Unix* (`PG_SOCKET`, défaut `/tmp`) ; un
  rôle `partiduo` avec `CREATEDB` (`provision` le crée au besoin),
  authentification `peer` ;
* l'utilisateur ssh de déploiement peut `sudo` (`security/sudo`) ;
* nginx, dont `nginx.conf` inclut `partiduo/*.conf` dans le bloc `http` ;
  `acme.sh` (`/usr/local/sbin/acme.sh`), son utilisateur `acme`, son cron de
  renouvellement (`/usr/local/etc/cron.d/acme`) et la règle sudo de
  rechargement de nginx (`/usr/local/etc/sudoers.d/acme`), par la recette beryl
  `acme` ; le DNS de `<dossier>.<domaine>` pointe sur le serveur
  (défi HTTP-01) ;
* `curl` pour le contrôle de santé.

Rien de cet outillage n'a encore été exécuté contre un serveur réel : les
specs (`spec/deploy/scripts_spec.cr`) vérifient les plans et la génération
des fichiers.
